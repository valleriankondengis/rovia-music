# Database Mechanism

## Lifecycle

`AppContainer` holds the database as a lazily created singleton.
`RoviaDatabaseFactory.create()` applies double-checked locking around
`Room.databaseBuilder` for the file `rovia.db`, sets
`AndroidSQLiteDriver` and a `Dispatchers.IO` query coroutine context, and
builds the `RoviaDatabase` instance. The database class exposes one abstract
function per DAO; consumers receive the database (or a repository built on
it) from `AppContainer` and never build their own instance.

The schema is version 1 with `exportSchema = true`. The builder registers no
migrations and no destructive fallback, so the exported schema in
`app/schemas/` is the exact contract the installed database is created from.

## Schema layout

The 19 tables fall into four groups.

### Catalog

The device's music library, reconciled from MediaStore:

- `tracks` — one row per audio file, with metadata snapshots (title, artist
  credit, album title, release date parts), MediaStore identity
  (`mediaStoreId`, `volumeName`, `contentUri`), file facts (duration,
  relative path, dates) and availability.
- `artists`, `albums`, `genres` — the browsable catalog entities.
- `track_artist_cross_ref`, `album_artist_cross_ref`,
  `track_genre_cross_ref` — many-to-many relations between the catalog
  entities.
- `artwork_assets` — artwork descriptors referenced by foreign key from
  `tracks` and `playlist_tracks`.

### User library

Data the user creates inside the app:

- `playlists` — named playlists with creation and update timestamps.
- `playlist_tracks` — playlist membership with an explicit `sortOrder` and
  per-row snapshots of track title, artist credit, album title and artwork
  source.
- `liked_tracks` — liked songs, keyed by track with a `sourceKey` snapshot
  and a `likedAt` timestamp.
- `liked_entities` — liked artists, albums, singles and EPs, keyed by
  `(entityType, entityKey)` with title, subtitle and artwork snapshots and a
  `likedAt` timestamp.

### Playback records

What the player has played, written as playback happens:

- `playback_activities` — per-track activity summaries read by the history
  feature.
- `playback_sessions` — one row per playback session.
- `playback_track_events` — per-track events inside sessions.
- `listening_segments` — listened intervals used by playback statistics.
- `user_action_events` — generic user action records (schema only; see the
  note in [features.md](features.md)).

### App state

- `media_store_sync_state` — singleton state rows (`REPLACE` on conflict)
  recording catalog synchronization progress.
- `excluded_folders` — folder exclusion rows (schema only at runtime; see
  [features.md](features.md)).

## Identity model

Every table uses an autogenerated surrogate primary key (`trackId`,
`playlistId`, and so on). A track additionally carries:

- `sourceKey` — a unique, stable string identity with a unique index, used
  wherever a durable reference to a track is stored (for example in
  `liked_tracks`).
- The MediaStore identity pair (`mediaStoreId`, `volumeName`), indexed
  together. The UI layer's `LocalAudioTrack.id` is the MediaStore id, not
  the Room `trackId`; repositories resolve between the two through
  `TrackDao.getByMediaStoreIdentity`, with `TrackDao.getById` as a fallback
  for rows that already carry a database id.

## Snapshot and deletion rules

User data must survive catalog churn, so membership rows snapshot what they
reference instead of depending on it:

- Foreign keys from `playlist_tracks` and `liked_tracks` to `tracks` use
  `onDelete = SET_NULL`. When a file leaves the catalog, the playlist or
  liked row stays, keeps its snapshots for display and search, and is
  skipped when a playable queue is assembled.
- Deleting a playlist cascades to its `playlist_tracks` rows
  (`onDelete = CASCADE` on the playlist foreign key).
- `liked_entities` holds no track foreign key at all; it keys on the
  entity's own identity (artist name or release key) plus snapshots.
- Catalog foreign keys that would dangle (track → album, track → artwork
  asset) also use `SET_NULL`.

## Write paths

- **Catalog**: `MediaStoreCatalogSynchronizer` scans MediaStore and
  reconciles the catalog tables — inserting with `IGNORE` so existing rows
  keep their identity, updating changed rows, and removing rows whose files
  disappeared. Each run records its progress in `media_store_sync_state`.
- **User library**: `UserLibraryRepository` performs playlist, liked-track
  and liked-entity writes. Adding a track to a playlist checks for an
  existing membership first and rejects duplicates rather than relying on a
  constraint.
- **Playback records**: `PlaybackService` writes sessions, track events and
  listening segments through their DAOs while playback runs.

There are no explicit multi-statement transactions. Writes that belong
together are issued in sequence by the owning repository or synchronizer,
and each DAO call commits independently.

## Read paths

Repositories expose two shapes:

- `Flow` queries for observed data — library lists, playlist detail, liked
  state, search results — so the UI updates when the underlying tables
  change.
- `suspend` one-shot reads for actions (resolving a track, checking a like,
  assembling a queue).

Ordering is expressed in the queries themselves: liked lists read
`likedAtEpochMillis DESC`, playlist contents read `sortOrder ASC`, and catalog lists
read their normalized title columns, which carry their own indexes.
